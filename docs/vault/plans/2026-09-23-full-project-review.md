## 1. Итоговая оценка (честно)

**Коротко: это сильный инженерный прототип, но ещё не коммерческий B2B-продукт.**

| Направление | Оценка | Комментарий |
| --- | --- | --- |
| Инженерия / код | 6.5 / 10 | Домен вынесен в `src/domain` и покрыт тестами — это хорошо. Минус: экраны-монолиты по 2 000+ строк, 78 warnings, e2e почти нет. |
| Продукт / B2B-ценность | 4 / 10 | **Монетизация отсутствует в коде.** Магазин не видит денег — только счётчики сканов. |
| Данные (ядро ценности) | 4.5 / 10 | EAN-база зашумлена, trusted-алиасов 0, а покупатель не видит уровень достоверности. |
| UI / UX | 6 / 10 | Много сделано и сделано аккуратно, но хардкод цветов, заглушки, два разных AI-чата. |
| Безопасность | 5.5 / 10 | service-role только на сервере, вебхуки с секретом — плюс. Минус: анонимные загрузки, обходимый rate limit, `anon` пишет в `missing_products` и читает RAG-базу, 24 уязвимости в зависимостях. |
| **Итого** | **≈ 5.5–6 / 10** | Продавать можно только после P0-блока ниже. |

Главная системная проблема: **продукт оптимизирован под «feature completeness», а не под
«магазин платит и покупатель находит товар»**. Дашборд считает сканы, не деньги; сканер
фактически работает только по точному совпадению EAN; уверенность данных нигде не
показана. Плюс есть экран, сломанный на 100 % (см. P0-1) — это симптом отсутствия
регрессионного контура на ключевых пользовательских путях.

## 2. P0 — блокеры

### P0-1. Экран сравнения полностью сломан: `activeSlug is not defined`

- **Файл:** `src/screens/CompareScreen.jsx:408`, `src/screens/CompareScreen.jsx:411`
- **Роут:** `/s/:storeSlug/product/:ean/compare/:ean2`
- **Причина:** в `useParams` деструктурируется `storeSlug` (строка 261), а в
  `handlePrimaryAction()` используется несуществующая переменная `activeSlug`.
- **Воспроизведение:** открыть сравнение двух товаров → нажать главную кнопку действия
  («Спросить AI» / переход к альтернативам при блокировке).
- **Фактическое поведение:** `ReferenceError: activeSlug is not defined`. Глобальный
  `ErrorBoundary` (`src/App.jsx:99`) показывает заглушку вместо белого экрана, но сценарий
  недоступен всегда, при любых входных данных.
- **Почему не поймано:** ESLint сообщает об этом как **`no-undef` warning** (не error) →
  CI зелёный; unit-тест `compareScreenStructure.test.mjs` проверяет структуру исходника, а
  не поведение; e2e на этот роут нет.
- **Фикс:** заменить `activeSlug` на `storeSlug` (паттерн соседних экранов —
  `ProductScreen.jsx:467`, `AlternativesScreen.jsx:284`).
- **Регрессионный тест:** e2e-кейс «открыть compare → кликнуть primary CTA → URL содержит
  `/s/<slug>/product/<ean>/ai`». Плюс поднять `no-undef` до error.

### P0-2. Монетизация не реализована: тариф нигде не enforced

- **Файлы:** `src/screens/SuperAdminStoresScreen.jsx:375` (`plan_expires_at` — поле CRM),
  `src/screens/RetailSettingsScreen.jsx:613-615` (владелец сам переключает `is_published`),
  `supabase/KORSET_DB_SCHEMA_FULL.sql` (поля плана/биллинга есть только в дампе схемы).
- **Факт:** поиск по `src` показывает **0 мест**, где `plan_expires_at` / `trial` /
  `subscription` влияют на доступ. Поля есть, логики нет.
- **Следствия:**
  1. Магазин с истёкшим планом продолжает работать полностью.
  2. Магазин может сам опубликовать витрину (`is_published`) без оплаты и без модерации.
  3. Нет лимитов по тарифу (товары, сканы, AI), нет страницы биллинга, нет оферты.
- **Оценка:** это самый дорогой риск проекта. B2B2C-модель существует только в документах.
- **Фикс:** план-энфорсмент на сервере (не в клиенте): проверка `plan_expires_at` в
  `store-seo.js` / в RLS / в RPC выдачи каталога, экран биллинга, лимиты тарифа, публикация
  витрины — только после подтверждения оплаты админом.

### P0-3. Анонимная загрузка файлов в публичный бакет без лимитов

- **Миграция:** `supabase/migrations/057_submissions_storage_policy.sql` — политики
  `INSERT`/`UPDATE` для роли `anon` на `public-assets/submissions/*` без проверки размера,
  типа и количества.
- **API:** `api/submit-product.js` — **нет аутентификации и нет rate limit**; принимает до
  5 изображений × 3 МБ за запрос (строки 108-129), количество запросов не ограничено.
- **Дополнительно:** ответы об ошибках отдают внутренности БД клиенту —
  `insertError.message` и `insertError.hint` (строка 191) и `err.message` (строка 206).
- **Вектор:** анонимный ключ Supabase публичен (в клиентском бандле), значит загрузку можно
  делать напрямую в Storage REST в обход API-лимитов → исчерпание хранилища и размещение
  произвольных картинок на CDN-домене проекта.
- **Фикс:** загрузки только через авторизованный/разовый токен (или captcha), серверная
  валидация MIME/размера/числа файлов, лимит на IP+store, generic-ответы об ошибках
  (`errorCode` без `message`/`hint`), Storage-политика с проверкой `metadata.size`.

## 3. P1 — серьёзные риски

### P1-1. Ядро продукта (скан у полки) опирается только на точное совпадение EAN

- **Файл:** `src/domain/product/eanAliases.js:51-56` — алиас резолвится только при
  `status === 'trusted' && confidence >= 80`.
- **Контекст из `docs/CONTEXT.md` §5:** загрязнённые `alternate_eans` (146 805 алиасов,
  81.4 % critical), **Trusted = 0**, 144 856 строк в карантине, база штрихкодов ЕАЭС
  практически пуста.
- **Итог:** весь слой алиасов выключен. Покупатель сканирует товар, которого нет в базе по
  точному EAN → «не найдено», хотя товар в каталоге магазина может быть. Это бьёт ровно в
  главную ценность продукта.
- **Что сделать:** измерить реальный hit-rate сканов по магазинам (процент `not_found`),
  поднять trusted-промоушен (ручная модерация кандидатов в `EanRecoveryScreen`), и только
  потом судить. Сейчас метрики нет — решение принимается вслепую.

### P1-2. Не поддерживаются 12-значные UPC-A и 14-значные EAN/ITF-14

- **Файл:** `src/screens/ScanScreen.jsx:1009` — ручной ввод принимает только 8 или 13
  цифр; строка 1242 обрезает ввод до 13 символов.
- **Нет нормализации:** `padStart` в проекте встречается один раз и не для штрихкодов
  (`AIAssistantScreen.jsx:525`) → UPC-A не дополняется до EAN-13 ни при сканировании, ни
  при ручном вводе.
- **Несогласованность:** бэкенд принимает 8-14 цифр (`api/submit-product.js:20`
  `VALID_EAN`), клиент — только 8/13.
- **Влияние:** импортные товары (маркировка UPC-A) покупатель найти не может ни сканом, ни
  руками.
- **Фикс:** единый нормализатор EAN (UPC-A → 0+EAN13, допуск 8/12/13/14), переиспользовать
  его в ScanScreen, ProductScreen и при логировании сканов; покрыть тестами.

### P1-3. Первая загрузка витрины: весь каталог в память, O(n²) копирований

- **Файл:** `src/contexts/StoreContext.jsx:315-345`.
- **Что происходит:** цикл батчей по 1000 строк до ~10 228 товаров; на каждой итерации
  `setFullCatalog([...allProducts])` → до 10 полных ре-рендеров дерева и квадратичное
  копирование массива; затем запись ~10 К строк в IndexedDB. Эффект зависит от
  `[currentStore?.id, isOnline]` → при флапе сети всё повторяется.
- **Риск:** на массовом Android это долгий первый экран и фризы — ровно то, что убивает
  сценарий «перешёл из 2GIS, быстро посмотрел цены».
- **Фикс:** не публиковать промежуточные состояния в React-стейт (копить в локальную
  переменную, один `set` в конце), виртуализация/пагинация выдачи, инкрементальное
  обновление IndexedDB, явный индикатор прогресса.

### P1-4. Rate limit AI обходится, хранилище растёт бесконечно

- **Файл:** `api/ai.js:53-71`.
- Ключ лимита для анонимов — **первый `X-Forwarded-For` из заголовка**, то есть
  подконтролен клиенту: меняешь заголовок — получаешь новую квоту.
- Сам счётчик — `Map` в памяти инстанса: сбрасывается на cold start, не шарится между
  инстансами (Vercel), и **никогда не очищается** (рост памяти инстанса).
- **Следствие:** лимит 8 req/min для анонимов защищает бюджет OpenAI только номинально.
- **Фикс:** внешнее хранилище (Vercel KV / Upstash Redis / таблица в Supabase), ключ от
  доверенного источника (не сырой XFF), TTL-очистка, общий бюджет по дням + алерт.

### P1-5. `/api/sentry-webhook` без аутентификации

- **Файл:** `api/webhooks.js:78-107`; маршрут проброшен в `vercel.json`
  (`/api/sentry-webhook` → `/api/webhooks`). CORS: `Access-Control-Allow-Origin: *`.
- Любой может отправить POST с произвольным «Sentry FATAL» и ссылкой → сообщение уйдёт в
  Telegram оператора. Вектор: алерт-фэтigue и фишинг на живого оператора.
- Контраст: Telegram-вебхук защищён корректно (`verifyWebhookSecret`, строка 721) — то есть
  проблема именно в Sentry-ветке.
- **Фикс:** общий секрет в заголовке/query для Sentry-ветки, ограничение источника.

### P1-6. Покупатель не видит достоверность данных (аллергены / халал!)

- **Факт:** `sourceConfidence` / `qualityScore` / `aiEnriched` вычисляются в доменном слое
  (`src/domain/product/normalizers.js`, `resolver.js`, `model.js`), но в UI-компонентах —
  **0 упоминаний** (grep по `src`).
- **Риск:** Fit-Check по аллергенам и халал-статусу может быть построен на AI-догадке, а
  покупатель видит его как проверенный факт. Для аллергий это не UX-проблема, а
  безопасность.
- **Фикс:** бейдж источника в `ProductScreen` (проверенные данные / предварительные /
  AI-оценка), порог `qualityScore` для показа полного Fit-Check, отдельный текст
  «проверьте упаковку» при низкой уверенности.

### P1-7. Двуязычные строки Fit-Check живут вне системы i18n

- **Файл:** `src/utils/fitCheck.js` — 40 хардкодных пар `text` / `textKz` (например строки
  419-420, 429-430).
- **Следствия:** `scripts/check-i18n.mjs` их не видит (проверка «пройдена», но покрытие
  неполное); нет плюрализации и интерполяции; KZ-тексты рассинхронизируются с RU при
  правках.
- **Фикс:** вынести строки в `src/locales/{ru,kz}` и передавать `t` в `checkProductFit`
  (либо возвращать ключи и переводить на слое UI).

### P1-8. «Удалить аккаунт» не работает: FK без ON DELETE CASCADE

- **Файл:** `api/delete-user.js:71` — `admin.auth.admin.deleteUser(user.id)`; комментарий в
  коде сам оговаривается: «cascade will clean profiles via FK **if set**».
- **Схема:** `supabase/KORSET_DB_SCHEMA_FULL.sql:216` —
  `users_auth_id_fkey FOREIGN KEY (auth_id) REFERENCES auth.users(id)` — **без ON DELETE**
  (поведение по умолчанию NO ACTION). Аналогично `stores.owner_id → auth.users(id)`
  (строка 194).
- **Следствие:** удаление пользователя из Auth либо падает с нарушением FK (клиент получает
  500 `delete_failed`, аккаунт остаётся), либо, если профиля нет, проходит — но в любом
  случае `public.users` с PII (имя, `device_id`, preferences) не удаляется каскадом.
  Миграция 013 чинит каскады **внутри** public-схемы (`user_favorites` → CASCADE), но не
  связь `public.users → auth.users`.
- **Влияние:** юридически значимый флоу (удаление персональных данных) сломан для всех
  пользователей с профилем.
- **Фикс:** добавить FK `public.users.auth_id → auth.users(id) ON DELETE CASCADE` (и решить
  про `stores.owner_id` — там каскад нежелателен, нужен SET NULL/блокировка), затем
  явное удаление/анонимизация связанных данных в `api/delete-user.js`; покрыть тестом на
  БД-уровне и e2e «удалить аккаунт → профиля нет».

## 8. Ограничения этого ревью

Выводы основаны на исходниках и локальных чеках. Не подтверждено на живых данных:
реальный hit-rate сканов, состояние RLS в production, визуальное/perf-поведение на
устройствах, применённость миграций 050-057. Пункты P1-1 и P0-2 помечены как «риск по
коду + документации» — перед большими переделками стоит получить цифры из БД
(доля `not_found` в `scan_events`, число trusted-алиасов).

Оговорка по схеме БД: выводы по FK/RLS взяты из `supabase/KORSET_DB_SCHEMA_FULL.sql` и
миграций `supabase/migrations/0*.sql`; дамп схемы может отставать от фактической БД. Для
P1-8 это проверено дополнительно: ни одна миграция не меняет `users_auth_id_fkey`, так что
отсутствие `ON DELETE CASCADE` почти наверняка сохраняется — но перед фиксом стоит
свериться с `information_schema` в production.
