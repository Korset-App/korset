## Исправленные сценарии

- Смена магазина очищает прежние цены и товары до получения нового ответа; поздний ответ и сохранение настроек прежней точки не заменяют выбранную точку. Каталог и рекомендации учитывают магазин при задержке ответа и возврате к кэшу.
- Пустое наличие остаётся неизвестным; недопустимое непустое значение не превращается в отсутствие товара. Ошибка сохранения неизвестных товаров отражается как неудачная запись. Ошибка автоматического сопоставления после успешного сохранения показывается отдельно: товар уже в очереди.
- Локальный гостевой список доступен без регистрации. Копирование из другой точки без сети использует сохранённые данные, не делает обречённый запрос названия магазина.
- Подтверждённый добавленный сахар имеет приоритет над противоречащим тегом. Низких углеводов недостаточно для безусловного подтверждения кето без остальных требуемых сведений. Положительный ответ по халяльности или жирности не скрывает неизвестный состав для выбранного веганства/вегетарианства. Безлактозное молоко не объявляется безопасным при аллергии на молочный белок.
- Публичные ошибки отправки не раскрывают сообщения, подсказки и внутренние коды базы или названия отсутствующих ключей. Фотографии переходят через существующий серверный обработчик; повреждённый тип/содержимое, избыток фотографий и ошибка загрузки не дают ложного успеха.
- Изолированные браузерные проверки кабинета ждут готовности экрана, а внешний снимок фотографии получает локальную подмену. Это исправление проверки, а не доказательство доступности реального внешнего фото.

## Выпуск защиты фотографий

Рабочая политика `Public submissions upload` пока разрешает прямую загрузку гостю и авторизованному клиенту. Публичный контейнер уже ограничен JPEG/PNG/WebP и 5 МБ; это не ограничивает число загрузок в обход серверного обработчика. Смена клиента подготовлена, но не опубликована.

SQL `supabase/release-gates/2026-10-11-submissions-server-only.sql` сознательно находится вне автоматически применяемых миграций. Он оставляет разрешение серверной роли и закрывает прямую клиентскую запись. Девять локальных проверок подтверждают отказ клиентам на добавление и замену фото, сохранение чтения, серверной загрузки, независимой политики аватаров и применение к схеме без старой политики обновления. В рабочей базе старой политики обновления сейчас нет; условное ограничение сохраняет безопасность свежей схемы из миграции 057.

Порядок выпуска:
1. Просмотреть отдельный коммит исправлений; публиковать через согласованный GitHub → Vercel.
2. Проверить наличие серверных переменных в среде Vercel без вывода ключей. В тестовом окружении проверить отправку гостем с фотографией, идентификатором заявки и сохранённой ссылкой; локальные проверки этого не доказывают.
3. Проверить, что опубликованный клиент использует `/api/submit-product`, затем отдельно применить SQL ограничения политики и записать фактическую версию миграции.
4. Повторить разрешённую отправку через сервер и отказ прямой записи, проверить старые ссылки и аватары. Клиент со старым кэшем при ограничении потребует обновления; не включать политику до обновления приложения.

Серверный ключ остаётся только на сервере. Восстановление прежнего широкого доступа не является безопасным способом исправить выпуск. Ограничитель частоты запросов пока хранится в памяти одного процесса; распределённое ограничение и уборка неполных загрузок — отдельные улучшения. Основание механизма ролей: [документация Supabase Storage](https://supabase.com/docs/guides/storage/security/access-control).
