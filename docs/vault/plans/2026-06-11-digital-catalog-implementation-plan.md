# Мастер-план реализации: Цифровизация каталога (Digital Storefront)

Этот документ является главным источником правды для всех ИИ-агентов и сессий по ходу реализации стратегического перехода проекта Körset от закрытого мобильного ассистента к публичному цифровому каталогу (витрине) магазинов. Он содержит зафиксированные решения, этапы работы, архитектуру ИИ и разбор 5 критических подводных камней.

---

## 1. Суть стратегического поворота (Vision)

**Körset переориентирован с модели «закрытого ассистента покупателя у полки» на модель «публичной цифровой витрины магазина (Digital Storefront) + умного ассистента поверх неё».**

### Ключевые аспекты стратегии:
1. **Ценность для B2B (магазинов):** Владельцы получают готовую страницу каталога товаров с ценами (например, `korset.kz/s/mars`), ссылку на которую они могут разместить в своем профиле 2GIS (картах), Instagram или отправлять в WhatsApp.
2. **Потребительский слой (B2C):** Покупатели могут пользоваться каталогом, поиском, проверкой состава и диет (Fit-Check) и ИИ-ассистентом **без обязательной регистрации**. Регистрация — это лишь опциональный шаг для облачного сохранения списка покупок.
3. **Сканирование штрихкодов:** Сканер штрихкодов (barcode scanner) переходит из роли главного экрана в вспомогательную функцию быстрого поиска у магазинной полки.

## 2. Архитектура искусственного интеллекта (Azure AI Hybrid Scheme)

В целях оптимизации затрат (Cost Leakage) и использования спонсорского гранта Microsoft Azure AI Foundry, в проекте настроена гибридная схема моделей искусственного интеллекта:

*   **Чат-ассистент:** `DeepSeek-V4-Flash` (через OpenAI-совместимый шлюз Azure). Самая экономичная и быстрая текстовая модель, закрывающая 95% диалогов.
*   **Распознавание изображений (Vision):** `gpt-4o-mini` (Azure OpenAI) — используется для анализа упаковок и распознавания товаров по фото.
*   **Распознавание голоса (Transcription):** `gpt-4o-mini-transcribe` (сервис Whisper) — для голосового ввода покупателей.
*   **Векторные эмбеддинги (Embeddings):** `text-embedding-3-small` (Azure OpenAI) — для генерации векторов базы знаний (RAG / pgvector).
*   **Лимиты и контроль:** Вся логика обращается через единый Vercel Serverless прокси `/api/ai`. Введен жесткий лимит затрат в **10 долларов** на балансе Azure для предотвращения перерасходов.

## 3. Пять критических подводных камней и их решения

При переходе на публичные витрины были выявлены 5 ключевых технических и продуктовых рисков, решения для которых зафиксированы ниже:

### 1. Проблема шеринга в SPA (React) и Open Graph
*   **Проблема:** Приложение построено как SPA (Single Page Application - одностраничное приложение на React + Vite). Если менять meta-теги динамически на клиенте (через `react-helmet-async`), роботы-парсеры (Telegram, WhatsApp, Instagram) не увидят их, так как они не исполняют JavaScript, а читают сырой HTML. Превью ссылки (картинка, цена, заголовок) отображаться не будут, что убьет виральность.
*   **Решение:** Написать Edge/Serverless-функцию Vercel, которая перехватывает входящие запросы ботов по адресу `/s/*/product/*`, запрашивает информацию о товаре из Supabase и возвращает статический HTML с заполненными Open Graph (OG) тегами (`og:title`, `og:image`, `og:description`) напрямую, до загрузки основного бандла React.

### 2. Ограничения In-App браузеров (Instagram / TikTok)
*   **Проблема:** Ссылки из Instagram открываются во встроенном браузере приложения. Пользователи соберут свой "Список покупок" (хранящийся в `localStorage` встроенного веб-вью). Когда они придут в магазин и откроют Chrome/Safari или камеру, их список окажется пуст, так как хранилища разных браузеров изолированы.
*   **Решение:** Внедрить в экран «Списка покупок» детектор встроенного браузера (по User-Agent) и показывать заметный баннер: *«Вы открыли каталог через Instagram/TikTok. Чтобы не потерять список покупок, откройте страницу в основном браузере устройства или войдите в аккаунт»*.

### 3. Ожидания от «Списка покупок» и различие цен
*   **Проблема:** Если в списке покупок выводить итоговую сумму (например, 5 товаров на 3500 тенге), а магазин изменит цену на товар на следующий день, покупатель придет на кассу и столкнется с несовпадением сумм, что вызовет негатив.
*   **Решение:** В списке покупок **не считать общую сумму**, либо выводить крупное предупреждение: *«Примерная сумма. Цены в магазине могут отличаться от цен на кассе»*. Предпочтителен вариант без подсчета суммы на первом этапе для максимального упрощения.

### 4. Уязвимость RLS и режим черновиков (Stores Draft Mode)
*   **Проблема:** Магазины в процессе наполнения каталога не должны быть видны случайным пользователям, чтобы не компрометировать неполные цены и защитить данные от парсеров конкурентов.
*   **Решение:** Добавить статус магазина (`is_published` / опубликован). Но вместо усложнения фронтенда, применить жесткие политики Row Level Security (RLS - безопасность на уровне строк) в Supabase. Если магазин неопубликован (`is_published = false`), API Supabase (и RPC-функция `fn_get_store_catalog`) должны отдавать пустой массив или ошибку для неавторизованных анонимных пользователей. Для супер-администратора и владельца магазина доступ должен сохраняться. (Пока пилот тестируется в ручном режиме, черновики упрощены: магазин работает по прямой ссылке, так как без QR/2GIS трафика на нем все равно не будет).

### 5. Формат CSV при импорте цен ритейлерами
*   **Проблема:** Владельцы выгружают прайсы из 1С в CSV/Excel. Штрихкоды (EAN) при этом часто экспортируются в экспоненциальном виде (например, `4.82E+12`), теряют ведущие нули или содержат лишние пробелы. Это ломает сопоставление товаров.
*   **Решение:** Парсер CSV в Retail Cabinet (кабинете продавца) должен быть максимально дуракоустойчивым:
    *   Удалять пробелы из строк EAN.
    *   Восстанавливать научный экспоненциальный формат (`E+12`) обратно в полную числовую строку.
    *   Дописывать ведущие нули в начало строки до стандартных 13 символов (EAN-13).
    *   Выводить отчет об импорте: *«Обработано 1000 строк. 950 цен обновлено. 50 штрихкодов не найдены в вашем каталоге»*.

## 4. Фазы реализации каталога и их статус

### 🟢 Фаза 1: Инфраструктура, Панель Супер-Админа и Имперсонация (Завершено)
*   **СУБД миграции:**
    *   `050_hide_out_of_stock_catalog.sql` — RPC `fn_get_store_catalog` скрывает товары `out_of_stock`.
    *   `051_superadmin_auth_and_stores.sql` — колонка `is_superadmin` в `public.users` защищена триггером и добавлена в JWT.
    *   `053_admin_stores_metrics_rpc.sql` — RPC `fn_admin_get_stores_with_metrics` для сбора метрик магазинов.
*   **Серверный слой:**
    *   `api/admin-stores.js` — CRUD операции для супер-администратора (list, create, update, owner-auth).
*   **Фронтенд (React UI):**
    *   Экран [SuperAdminStoresScreen.jsx](file:///c:/projects/korset/src/screens/SuperAdminStoresScreen.jsx) — кабинет администратора: создание магазина, генератор пароля, привязка владельца, метрики (количество товаров, сканирования, ошибки).
    *   Имперсонация в [RetailLayout.jsx](file:///c:/projects/korset/src/layouts/RetailLayout.jsx) и [StoreContext.jsx](file:///c:/projects/korset/src/contexts/StoreContext.jsx) — супер-администратор может беспрепятственно просматривать и редактировать Retail Cabinet любого магазина без авторизации под его владельцем.

### 🟡 Фаза 2: Рост и виральность (SEO & Sharing) (В процессе — выполнено на 50%)
*   **Сделано:**
    *   Настройка `robots.txt`, `sitemap.xml` и `/api/sitemap.js`.
    *   Концепция "Умного SEO" (индексация страниц магазина, но `noindex` для страниц товаров).
*   **Осталось сделать:**
    *   **SPA Open Graph пре-рендеринг:** Реализация функции-перехватчика Vercel для ботов Telegram/WhatsApp по пути `/s/*/product/*`.
    *   **Рефакторинг «Избранного» в «Список покупок»:**
        *   Замена терминов во всех локалях: `ru/*.json` и `kz/*.json`.
        *   Замена иконки `favorite` (сердечко) на `checklist`/`shopping_bag` в UI.
        *   Внедрение баннера-предупреждения для In-App браузеров (Instagram/TikTok).
        *   Предотвращение споров о ценах (убрать итоговую сумму или добавить предупреждение).

### 🔴 Фаза 3: Retail-инструменты для поддержки каталога (Планируется)
*   **Защищенный режим черновиков:**
    *   Добавление флага `is_published` в таблицу `stores` и обновление RLS-политик Supabase для защиты неопубликованного каталога.
*   **CSV импорт цен:**
    *   Разработка надежного парсера с автоматической коррекцией экспоненциального формата штрихкодов, удалением пробелов и добавлением ведущих нулей.

## 5. Дополнительные требования к разработке (Contracts)
*   **Язык программирования:** Строго JavaScript (не TypeScript), React 18, Vite.
*   **Стили CSS:** Чистый Vanilla CSS без использования TailwindCSS. Запрещено использовать жестко закодированные цвета фонов/текста (использовать CSS-переменные темы).
*   **Локализация (i18n):** Любой пользовательский текст должен быть переведен на русский (RU) и казахский (KZ) языки в соответствующих JSON-файлах в папке `src/locales/`.
*   **Безопасность:** Row Level Security (RLS) в Supabase должна быть включена и строго проверена при любых изменениях структуры таблиц.
