# Заполнение пищевого каталога: сбор, сопоставление и единая обработка 30 атрибутов

## Решение после пересмотра плана

Главная работа — получить недостающие сведения о существующих товарах.
Не приводить весь каталог к идеалу перед сбором. Одновременно переиспользовать
сохранённые источники и собирать новые сведения, затем пропускать их через один
общий процесс извлечения, сопоставления и проверки. Готовые партии можно переносить
по мере появления; не ждать, пока будут заполнены все 30 полей у всех товаров.

Подготовлен план, выполнены локальные подсчёты и агрегирующее чтение рабочей базы.
В ночном этапе собраны три официальных источника, но производственные изменения
не выполнялись. Перенос согласуется по AGENTS.md на основании конкретной
проверенной партии. Платные вызовы моделей не запускались.

исправлен и покрыт тестом. Старый checkpoint Open Food Facts сообщает 13 223
обработанных кода и 15 обогащений — повторять тот же проход без новой гипотезы
неэффективно.

## Что в прежней работе действительно мешало заполнению

Источники истории: планы и журналы V4 от 24–26 сентября, майские отчёты по источникам,
инструкция обхода Arbuz, существующие скрипты, полные локальные выгрузки и журналы
сопоставления. Старые отчёты «всё завершено» проверяются по файлам; их цифры не
переносятся в текущий отчёт как факты. Полный архив всех разговоров не прочитан.

Установленные по коду проблемы:

- Старый Arbuz обходил ограниченный список поисковых слов вместо полного дерева.
  Позднее отдельный проход нашёл штрихкоды и характеристики в данных страницы.
- У Galmart существовал предел страниц и неполный обход вложенных категорий.
- Корзина расширилась с 6 587 до 9 297 записей через дополнительный обход витрин.
  Старый резервный файл и новый полный файл не являются независимыми источниками.
- В разных программах пары отсекались по первому слову, отсутствующему бренду,
  недостаточному пересечению слов и нераспознанной фасовке; иногда оставался только
  один лучший кандидат. Бренд и фасовка нужны для решения, но их отсутствие
  не должно закрывать ВСЕ маршруты поиска кандидатов.
- Ошибка запроса модели может записываться как isMatch:false и затем пропускаться
  при повторе. Нужно различать «другая продукция» и «проверка технически не состоялась».
- Программа распознавания изображений ориентирована на товары без фото, поэтому
  её нельзя автоматически считать проходом обогащения нашей группы с фото.
- Импорт ignoreDuplicates:true пропускает существующие строки: локальное
  обогащение само по себе не обновляет рабочие карточки.
- В рабочей пищевой группе у 14 287 строк alternate_eans содержит собственный
  основной код. Исправление включить в общий перенос; не запускать отдельную
  многодневную очистку до сбора. Подробные старые заявления об исправлении
  этого дефекта не соответствуют свежему состоянию.

Артефакты истории: scratch/enrichment-source-history-20260927.*,
scratch/enrichment-matching-history-20260927.*. Одобрение модели не равно точности.

Полный подсчёт сохранённых файлов: Arbuz — 10 248 карточек, Корзина — 9 297,
Galmart — 2 859, KDV Online — 428. Эти количества не доказывают полный охват сайтов.
Журнал сопоставления: 12 445 строк, 6 932 разных основных кодов, 360 повторных
сочетаний цели/источника/имени донора, 33 сочетания с различающимися решениями.
Журнал изображений: 1 602 попытки; 607 завершились исчерпанием повторов.

Найдена конкретная ошибка адаптера Корзины: автономная программа берёт k.name,
тогда как файл хранит productName. Её исправление необходимо до нового поиска.
Повтор ограниченного старого поиска на текущем локальном наборе Arbuz/Корзина
оставляет 68 кандидатов. Это диагностическое воспроизведение части маршрута
на нынешнем состоянии журналов, не исторический результат всех источников.

Независимая перепроверка реального прироста точных пар Arbuz:
2 392 цели локальной фотопищевой группы совпадают по явному основному EAN;
только у 26 донор имеет числовое значение ИМЕННО недостающего нутриента —
всего 49 потенциально новых позиций КБЖУ. У 24 есть полный донорский набор при
неполном локальном, у 2 отсутствующий состав найден у донора. У 79 пар различаются
хотя бы какие-то уже заполненные числовые значения, поэтому копирование не автоматическое.
Исходный счётчик помощника 265 означал лишь «у цели что-то отсутствует, у донора
что-то есть» и завышал полезный прирост; для решения использовать 26, не 265.
Артефакт исправленной проверки: scratch/enrichment-exact-gain-20260927.*.

Вывод: повтор только точного EAN-соединения почти исчерпан для ЛОКАЛЬНОГО V4.
Значительный рост требует исправленного поиска неточных названий, новых страниц
и источников. Перенос уже собранного из локального V4 в рабочую базу остаётся
отдельным большим резервом; его точный объём по рабочим EAN здесь не вычислен.

## Выбор между возможными путями

| Вариант | Решение и основание |
|---|---|
| Ещё раз запустить прежнее слияние без изменений | Не основной путь: прежние ограничения и пропуски сохранятся |
| Заново скачать все уже сохранённые страницы | Только для устаревших, отсутствующих или неполно извлечённых данных |
| Перепарсить сохранённое сырьё и расширить поиск пар | Первый дешёвый проход; проверять прирост, не обещать тысячи заранее |
| Исправить обход Arbuz/Корзины/Galmart и других магазинов | Параллельный сбор: новые ID, незакрытые страницы, скрытые характеристики |
| Добавить сайты производителей | Высокий приоритет для брендов с большим числом пробелов |
| Дать GPT самостоятельно искать каждый из 17 тысяч товаров | Только для остатка: дорого, повторы страниц и неудобное возобновление |
| Применить смысловой поиск по векторам | Второй канал поиска, если словарь и текстовый индекс теряют известные пары |
| Распознать все лицевые фотографии моделью | Не основной путь: на лицевой стороне часто нет состава и КБЖУ |
| Распознать читаемые оборотные этикетки | Для пробелов после текстовых источников; проверять связь с упаковкой |
| Каталоги поставщиков / коммерческие базы | Оценить пересечение по нашим кодам и права использования до оплаты |
| Фото от пилотных магазинов | Последний необходимый канал для локальных товаров без сетевых данных |

Проверка качества не откладывается полностью до конца: ошибочная пара при сборе
загрязнит сразу много полей. Нужны небольшие автоматические проверки при каждом
приёме данных, а полная общая приёмка выполняется один раз перед/после переноса.

## Единый процесс без двойной работы

Достаточно трёх локальных наборов: исходные записи источников, решения о парах,
собранные карточки-кандидаты. Новая архитектура базы для начала не нужна.

1. **Переиспользовать и собирать.** Один проход извлекает все доступные 30 атрибутов,
   исходный текст/данные страницы, адрес, ID, дату и фотографии. Разделять список
   товаров и подробную карточку; обходить вложенные категории, города и языки,
   когда они действительно дают новые записи. Проверять пагинацию и дубли ID.
2. **Найти несколько возможных пар.** Точный штрихкод; затем текстовый поиск
   несколькими независимыми способами. Для отсутствующего бренда есть запасной путь.
3. **Подтвердить товар и извлечь значения.** Лёгкие однозначные случаи — правила;
   трудные — модель со сведениями об обеих сторонах, несколько кандидатов и право
   ответить «нет пары» или «недостаточно данных». Сильная модель — только для споров.
4. **Нормализовать один раз.** Общие правила единиц, состава, категорий и применимости
   работают и для старого сырья, и для нового. При изменении правил переобрабатывать
   сохранённые исходники, а не снова скачивать сайт.
5. **Перенести готовую партию.** Предварительный список старое/новое/основание,
   согласование записи, резервные значения, обновление только нужных полей.
   Проверить чтением и пересчитать всю рабочую группу. Незакрытые поля продолжают
   идти по очереди источников, без повторной обработки уже подтверждённых.

Все журналы дописываются и сохраняют место продолжения. Ключ повторного использования:
источник + ID + версия содержимого + версия извлечения/решения. Сетевые ошибки
возобновляются; содержательные отклонения пересматриваются только при новых данных.
Сохранять исходники сразу при сборе — это недорогая защита от потери работы.

## Как исправить поиск пар

Поисковая нормализация не меняет оригинальное название: Unicode, регистр, ё/е,
казахские буквы, смешанная кириллица/латиница, пунктуация, порядок слов,
аббревиатуры и единицы. Параллельно хранить исходный текст и разобранные признаки.

Словарь подтверждённых вариантов бренда (Rakhat/Рахат и т.п.) пополняется из источников.
Не переводить свободно названия линеек и не удалять значимые признаки вкуса.
Упаковочные сокращения можно уменьшать по весу в поиске, сохраняя их для проверки.
Разобрать массу/объём, количество штук/пакетиков, наборы 6×100 г, жирность, вкус,
линейку, газированность, состояние продукта. Отсутствующая масса — неизвестность,
а не автоматическое несовпадение.

Объединить кандидатов из:
точного EAN и доказанных альтернатив; словарного поиска бренда/линейки;
поиска по словам без учёта порядка (BM25); сходства частей слов для опечаток;
транслитерации; при необходимости многоязычного смыслового поиска.
Ошибочная категория служит мягким признаком, не непреодолимым фильтром.
Получать несколько лучших кандидатов, расширять поиск для трудных карточек;
не ограничивать общее количество обрабатываемых товаров.

Решение о паре строгое: разные известные вкус, масса, жирность, рецептура или
упаковка означают конфликт. Отсутствие EAN у донора не запрещает сопоставление:
нужны доказательства идентичности конкретного товара по совокупности признаков,
при необходимости официальная страница/фото. Само сходство названий недостаточно.
Подтверждённые разные коды не превращать в альтернативные по решению модели.
Разные рынки и версии рецептуры проверять отдельно даже при одинаковом штрихкоде.

Измерять отдельно: долю целей с найденным кандидатом; сохранение известных точных
пар среди кандидатов; решения о совпадении; число реально добавленных атрибутов.
Повторить поиск для ВСЕЙ целевой группы, а не объявлять успех по нескольким примерам.
Для оценки ошибок модели можно использовать размеченную проверочную группу,
но она не подменяет отчёт о статусе каждой целевой карточки.

поля статусы: подтверждено / вычислено или переведено / справочно / неприменимо /
нет данных / конфликт. Не считать unknown, пустой объект или самодублирующий код
успешным заполнением.

## Однокомпонентность, КБЖУ и цель 90%

Подтверждённому простому продукту не придумывать многокомпонентный состав.
Однокомпонентность установить по источнику и виду продукта; название «молоко»
или «вода» само по себе не доказывает отсутствие добавок.

Справочное КБЖУ подходит для однозначно определённых простых продуктов с совпадающим
состоянием и съедобной частью. Показывать как справочное, отдельно от этикетки.
Не заменять им рецептуру фирменного соуса, йогурта, колбасы или выпечки.
Не смешивать 100 г и 100 мл, сырой/готовый продукт, кДж/ккал, массу нетто и порцию.
Нули допустимы только когда они явно даны источником.
Проверка энергии через БЖУ выявляет подозрения, но не переписывает этикетку сама.

Цель: >=90% качественно закрытых применимых составов и КБЖУ, а также совместно
готовых карточек. Для остальных 30 атрибутов — матрица покрытия и общий показатель
по применимым полям; не позволять названиям и фотографиям скрывать нехватку КБЖУ.
Справочные/переведённые/расчётные значения видны отдельно. Неприменимость имеет
причину; отсутствие источника не превращается в неприменимость. Проверить всю
целевую группу и показать остаток, а не экстраполировать маленькую выборку.

## Экономия и роль моделей

Парсеры скачивают и извлекают стандартные поля массово. GPT полезен для распознавания
вариантов названия, выбора среди нескольких кандидатов, сложного текста и этикеток.
Модель не должна выдумывать отсутствующие сведения или напрямую синхронизировать базу.

Luna low/medium — ограниченные подсчёты, подготовка признаков и простые пары.
Сильная модель — спорные пары и правила. Существующих поставщиков моделей
не заменять автоматически; сравнение альтернатив — на одних проверенных заданиях.
Показатели сравнения: пропущенные реальные пары, ложные совпадения, доля
«недостаточно данных», стоимость одного добавленного подтверждённого поля.

Для массовых независимых заданий рассмотреть Batch API, пакетные отложенные запросы.
Документация OpenAI указывает скидку 50% и выполнение в пределах 24 часов для
поддерживаемых моделей; доступность выбранной модели и лимиты проверяются до запуска:
https://developers.openai.com/api/docs/guides/batch .
Ответ по JSON Schema, заданной структуре, облегчает машинную проверку формата,
но не гарантирует истинность содержания:
https://developers.openai.com/api/docs/guides/structured-outputs .

Бюджет считать по измеренным токенам и текущим тарифам: извлечение + проверка пар +
изображения + поиск + повторы. Тестовая партия измеряет затраты и ошибки,
не доказывает качество необработанных товаров. Очередь охватывает весь набор;
при достижении бюджета сохраняет остаток и прогресс, а не молча отбрасывает товары.

## Ближайшее исполнение и критерии перехода

A. Подготовить улучшенный локальный поиск пар и общее извлечение 30 полей.
Результат: по всей группе — где уже есть донор, что можно добавить, что осталось,
какие старые фильтры потеряли пары. Исходные базы не переписывать.

B. Одновременно доработать наиболее полезные парсеры и подключить производителей.
Выбирать порядок по числу новых подтверждённых полей на стоимость; не ждать
полной проверки всех карточек, чтобы начать собирать недостающие данные.

C. Прогнать найденные пары, извлечь все поля за один раз, сформировать готовые
партии обновления. Конфликты остаются отдельной очередью. Не переносить один
нутриент из одной версии упаковки, а другой — из противоречащей версии.

D. После согласования перенести готовые партии, проверяя неизменность старых
значений перед записью, сохраняя откат и происхождение каждого нового поля.
Если существующих полей недостаточно для честного отображения справочных данных,
сначала предложить минимальное изменение и проверить всех потребителей.

E. Итоговая проверка всей группы, затем адресный добор остатка. Только после
стабилизации текущего набора расширение до 25–30 тысяч пищевых товаров по
ассортименту реальных магазинов и неизвестным сканированиям.

Смена чата допустима: новый исполнитель читает этот план и локальные отчёты,
продолжает конкретную очередь, не начинает новый общий аудит.
scratch — локальные артефакты; при смене компьютера их нужно передать отдельно.
