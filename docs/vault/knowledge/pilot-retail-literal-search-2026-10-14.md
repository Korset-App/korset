# Буквальный поиск каталога кабинета

В текущем каталоге ввод `(` разрушал экран: строка напрямую становилась шаблоном RegExp. Отдельно запятая попадала в структуру серверного OR, а не в защищённое значение. Два корректных браузерных воспроизведения: `../retail-literal-red-final-20261014.log`. Предшествующие неудачи выбора тестового поля не являются дефектами приложения.

`Highlight` экранирует введённые знаки перед построением шаблона; совпадения берутся по нечётным частям разделения, без изменяемой позиции поиска `regex.test`. Подсветка и её оформление сохранены.

В `getStoreCatalogProducts` глобальный поиск по имени/бренду и магазинный по местному имени/штрихкоду получают один буквальный шаблон в кавычках. Используется документированный `imatch` — сопоставление без учёта регистра; все знаки шаблона экранированы. Это сохраняет поиск подстроки и позволяет искать `%`, `_`, `*` буквально, вместо расширения совпадений через ILIKE. Второй уровень экранирования защищает кавычки и обратную косую черту в значении фильтра. Ограничения `store_id`, `is_active`, порядок и страницы сохранены; глобальные идентификаторы дополняют только ассортимент текущего магазина.

Официальные основания: [операторы PostgREST](https://docs.postgrest.org/en/stable/references/api/tables_views.html#operators) и [кавычки зарезервированных символов](https://docs.postgrest.org/en/stable/references/api/url_grammar.html#reserved-characters). Документация просмотрена в этом пакете. Это клиентское формирование запроса, без изменения схемы, правил доступа или индексов.
