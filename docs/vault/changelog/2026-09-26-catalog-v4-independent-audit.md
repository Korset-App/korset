# Независимый аудит каталога V4 — 26 сентября 2026

## Проверенные факты

- Локальный `data/korset_master_catalog_v4_final.jsonl`: 58 643 уникальные строки; 23 112 строк с URL фото; 16 251 непустой состав; 6 147 записей с четырьмя полями КБЖУ. 58 074 кодов имеют 13 цифр и проходят контрольную сумму; ещё 569 имеют 8 цифр и тоже проходят свою контрольную сумму. Длина и контрольная сумма не доказывают соответствие кода конкретному товару.
- Подмножество «с фото и категорией, отличной от `personal_care` и `household`»: 17 815 строк, состав — 11 475 (64,4%), полный КБЖУ — 4 222 (23,7%), оба поля — 4 101 (23,0%). Это предварительная верхняя оценка продуктового подмножества: ошибочные категории ещё не исключены.
- Фото в локальном файле: 22 961 URL на `semeiniy.kz`, 76 на Galmart, 58 на Arbuz, 14 на Open Food Facts, 3 на KDV. Наличие URL не подтверждает доступность ссылки или визуальное соответствие товара.
- Для всех 22 961 ссылок на фото `semeiniy.kz` найден тот же URL в исходной выгрузке под тем же EAN; имена совпали у 22 960 карточек. Это подтверждает техническую привязку к исходному товару, но не содержание самого изображения. Фото сейчас ссылаются на внешние сайты, а не на собственный R2/CDN проекта.
- Среди 58 фото Arbuz у 44 в URL есть 13-значный код; у 26 этот код не совпадает ни с основным, ни с альтернативными кодами карточки V4. Пример: карточка `4870082002638` («Набор шоколада Казахстанский 128гр») ссылается на файл `4870242600179_nabor_shokolada_rahat_250_g`. Это сильный сигнал неверного фото, а не доказательство ошибки всех остальных внешних ссылок. Два URL Galmart тоже содержат отличный код; их нужно проверить отдельно. Не синхронизировать внешние фото без проверки SKU и упаковки.
- Категории действительно повреждены: например, EAN `6944990111534`, женские колготки Innamore, имеет `category=grocery` и в локальном файле, и в рабочей БД. Парсер `scripts/crawl-semeiniy.mjs` отправляет нераспознанные категории в `grocery`; `scripts/prepare-master-v4-final.mjs` делает то же при пустой категории. Нельзя считать все 17 815 строк проверенными продуктами питания.
- Дополнительная проверка по точному EAN и исходным «хлебным крошкам» Semeiniy нашла минимум 1 412 явных категорийных ошибок в непересекающихся группах: 1 166 специй/бульонов в `grocery`, 222 колбасы/сосиски/паштета в `dairy_eggs`, 21 мясная закуска в `water_beverages`, 3 рыбные консервы в `grocery`. Это нижняя оценка, не полный процент ошибок. Причина — порядок широких проверок подстрок в `categorizeProduct`; `categoryMap.js` принимает уже заданную допустимую категорию без перепроверки.
- В рабочей Supabase на момент аудита: `global_products` — 58 648 строк (все активны), URL фото — 113, непустой состав — 12 292, полный КБЖУ — 106; `store_products` — 81 148 связей. Три проверенных EAN (`4870002960796`, `4870206414897`, `6944990111534`) сохраняют старые пустые поля при наличии более полных локальных данных.
- По магазинам видимые связи и фото: MARS — 58 648 / 113, Береке — 15 000 / 16, Нұрлы — 4 000 / 7, Калина — 3 500 / 4. Запрос витрины выводит только активные связи конкретного магазина и исключает `out_of_stock`. В рабочей БД MARS имеет 3 350 товаров категории напитков. Публичный `fn_get_store_catalog` по SQL возвращает все 58 648 строк, но тот же вызов через публичный API на первой странице даёт HTTP 500: `canceling statement due to statement timeout`. Фильтрация RPC по категории также дала HTTP 500 для пяти проверенных категорий. `EXPLAIN` показывает `Function Scan`: сначала вычисляется вся функция, потом применяется лимит страницы. Клиент `StoreContext.jsx` молча прекращает загрузку при ошибке. Это подтверждённая причина пустой витрины, а не отсутствие товарных строк.
- `scripts/seed-master-v4-to-supabase.mjs` загружает `global_products` с `ignoreDuplicates: true`. Существующие записи остаются старыми: это подтверждённая причина отставания рабочей БД от локального файла. Скрипт также назначает демонстрационным магазинам случайные цены и остаток `in_stock`; повторно запускать его для исправления реальных витрин нельзя.
- Локальные донорные выгрузки с собственным EAN (Arbuz, clean V2, aggregated V3, OFF) дают по точному совпадению с primary/alternate EAN V4 только 8 дополнительных составов и 111 полных наборов КБЖУ для предварительной группы из 17 815 товаров. Это потенциальные значения без проверки качества. Логи `*_matches.jsonl` не считались точными EAN донора: в них `masterEan` — уже назначенный код мастер-товара. Korzina v Dom, Galmart и KDV в проверенных схемах не дают надёжного собственного EAN. Следовательно, имеющиеся локальные доноры с доказанным EAN не закроют разрыв до 80%.
- Передаточный документ от 25 сентября сообщает устаревшие 13 360 составов и 2 272 КБЖУ. Его тезис о полном охвате активной витрины фото не подтверждён: локально фото есть у 23 112 из 58 643, критерий активности каталога там отсутствует (все 58 643 `is_active=true`).

## Не проверено

- Визуальное соответствие фото, целостность 23 112 удалённых изображений и реальная активность товаров в магазине «Семейный». Сайт источника и `korset.app` не удалось открыть из среды аудита. Предыдущая проверка 200 образцов не является доказательством для всего каталога.
- Доля ложных составов и КБЖУ после сопоставления доноров. Лог с одобрением модели доказывает только факт принятия пары моделью, а не идентичность упаковки. Нужна выборка с ручной верификацией по точным EAN, линейке, вкусу и весу.
- Точный внешний вид экрана и консоль браузера не проверены из этой среды. При воспроизведённом HTTP 500 клиент загружает запрос страницами по 1000 и при ошибке выходит без сообщения.

## Следующий безопасный порядок

1. Уточнить целевую когорту: только фасованные пищевые товары с подтверждённым кодом и проверенным фото; товары с ошибочной категорией вывести в очередь проверки. Не применять КБЖУ ко всем 58 643 строкам и не придумывать нули/составы.
2. Построить отчёт по каждому EAN: источник каждого поля, совпадение SKU, фото, состав, четыре поля КБЖУ, сомнения и статус проверки. Сначала точное совпадение заводского EAN; затем кандидаты по названию, бренду, вкусу, весу и формату с ручной проверкой на выборке. Подсчёт вести по *валидным* значениям, отдельно от просто непустых.
3. Проверить извлечение данных по каждому источнику на карточках с известными полями; измерить полноту кандидатов до этапа сопоставления. У прежнего `ai-text-consensus-merger.mjs` брендовый индекс исключает доноров без бренда, а порог пересечения токенов отсекает сокращённые названия. Поднять полноту поиска кандидатов без ослабления проверки соответствия SKU.
   Для 5 798 предварительных пищевых карточек с несколькими фото у 4 588 нет полного КБЖУ; сначала на стратифицированной выборке проверить, есть ли на оборотных фото читаемая таблица. Оптическое распознавание текста и проверка человеком могут дать дополнительные данные того же SKU, но объём потенциального прироста пока неизвестен.
4. После согласования исправления загрузчика: сравнить локальный файл с рабочей БД по EAN, сделать резервную копию и сухой прогон, обновить только подтверждённые поля с сохранением лучшего значения, проверить фото/состав/КБЖУ в БД и нескольких публичных карточках. Существующие магазинные цены, остатки и публикацию не генерировать заново.
5. После согласования изменения функции БД заменить полную материализацию `fn_get_store_catalog` пагинацией внутри SQL по устойчивому порядку и явными параметрами лимита/курсора. Сначала проверить `EXPLAIN`, публичное чтение первой и последующих страниц, время ответа для MARS и малых магазинов; затем обновить клиент. Добавить видимую обработку ошибки, чтобы пустая страница не маскировала отказ API.
6. Цели 80% и 90% считать только на очищенной когорте, с отдельной отметкой для товаров, у которых производитель не указывает состав или КБЖУ. Для текущих 17 815 строк до 80% не хватает 2 777 составов и 10 030 полных КБЖУ; до 90% — 4 559 и 11 812 соответственно. Эти числа пересчитать после очистки когорты.

Аудит выполнялся чтением локального файла и SQL `SELECT`. Рабочие данные не менялись.
